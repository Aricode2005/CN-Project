001DESK

Ask at the desk: one request, one response

RFC 9112 §2–§6 · message format

An HTTP request is a call slip: a request line (method target version), header fields, a blank line, and maybe a body. The answer comes back as a card with a status line, its own headers, and the resource. It's all plain text on a TCP connection. Fill in a slip and hand it over.

003COND
Has it changed? Conditional GET and 304
RFC 9110 §13 · ETag, Last-Modified

  
A reader who already has a copy shouldn't borrow the whole book again. The first answer carries validators (an ETag and Last-Modified). Next time the client asks only if changed. If nothing changed, the server sends 304 Not Modified: just headers, no body.

  
  







  
004CACHE
The reserve shelf: a caching proxy
RFC 9111 · freshness, validation, Via, Age

  
A university puts a web cache between its students and the slow Internet link. The first reader to ask for a page pays the WAN round trips (MISS). The copy goes on the reserve shelf, so the next reader gets it at LAN speed (HIT). When a copy's max-age runs out it becomes stale. The proxy then asks the origin "changed since?" and usually gets a 304 (REVALIDATED).

005STATE
Reader's ticket: cookies on a stateless protocol
RFC 6265 cookies · RFC 7617 Basic auth

  
HTTP forgets each request as soon as it's answered. To remember you, the server hands you a ticket (Set-Cookie: sid=…) and your client shows it on every later request (Cookie: sid=…). The state (who you are, what's in your cart) stays on the server; the cookie is only the key to it.
