Active vs passive: who lays the track?

PORT / EPRT · PASV / EPSV

In active mode the client says PORT ("connect to me here") and the server opens the data connection back to the client. In passive mode the client says PASV, the server answers 227 with a port, and the client opens the data connection. Turn on the client's firewall and see which mode survives. Both runs are real; press Forward ▶ to advance them side by side.

ASCII vs binary: TYPE A vs TYPE I

RFC 959 §3.1.1 · NVT-ASCII line endings

TYPE A (ASCII) treats the file as text and rewrites line endings: CR LF on the wire, the server's own ending on disk. TYPE I (image, binary) sends the bytes exactly as stored. Upload the same PNG both ways and download it back: binary is identical, ASCII breaks the image.

Resume a broken download: REST

RFC 959 §4.1.3 (REST) · RFC 3659 (SIZE, REST STREAM)

A 3 MB download breaks part-way (we send ABOR and the server replies 426, then 226). Instead of starting again, the client asks SIZE, sends REST <bytes we already have> (350), then RETR again, and the server continues from that byte. The two halves are joined and checked against the server's copy.

Security: what a sniffer sees

RFC 4217 (FTPS) · RFC 2577 (FTP security)

Plain FTP sends the password as text on the control connection. Our wire tap (port 2122) sits on the path like an attacker. Log in through it with plain FTP, then with FTPS: AUTH TLS encrypts the control connection before USER/PASS, and PROT P encrypts the data. Not to be confused with SFTP, a different protocol that runs inside SSH.

Plain FTPrun it
FTPSrun it
Bounce-attack protection (RFC 2577). A malicious client could send PORT with someone else's address, so the server would connect to a third machine for it. Our server only connects back to the client's own address, on a port ≥ 1024. Try PORT 8,8,8,8,0,80 in the console: 500 Illegal PORT command. The jail: CWD ../../.. can never leave the user's root.
